작성: NightShift-PM / 2026-11-01 00:36~00:38 KST 웹 도구 확인.
실제 수행은 공개 URL 열람과 검색이다. 게임 접속·플레이·개발자 연락·로그인·외부 메시지 전송은 하지 않았다. 페이지에 붙은 인기 수치·상품명·캐릭터·이미지·문구를 복제하지 않으며 아래 요약은 설계 패턴을 고르는 근거다. 재미·유지율·수익 개선은 모두 가설이다.

## 3. 권한·저장 제안의 공식 기술 근거

- [Roblox Data stores](https://create.roblox.com/docs/cloud-services/data-stores)를 실제 열었다. 서버에서 사용하는 영속 저장, `pcall` 오류 처리, 여러 서버의 동일 키 변경 시 `UpdateAsync` 사용 근거와 콜백의 비양보 제약을 확인했다. 이는 자동 원자 거래·자동 세션 잠금 보장이 아니다. 개인별 lease·revision·멱등성은 우리 계약에서 설계/검사해야 한다. 문서는 Studio API 접근이 기본 비활성이며 게시된 테스트 경험 설정을 설명한다. **이번 작업은 게시하거나 설정을 바꾸지 않았다.** 기존 승인된 테스트 환경이 없으면 클라우드 저장은 미검증으로 남긴다.
- [Securing the client-server boundary](https://create.roblox.com/docs/scripting/security/client-server-boundary)를 실제 열었다. 서버의 입력 타입·권한·거리·요청 빈도 검사, 비정상 수치 차단과 동시 처리/상품 복제 위험을 확인했다. 아래 계획의 입력·거래 검증은 이를 참고한 자체 설계 제안이며 보안 통과 증거가 아니다.

## 4. 채택 후보·대안·독립 검토 요청

| 후보와 가설 | 더 작은 대안 | 채택/축소 판단에 필요한 실제 검사 |
| --- | --- | --- |
| 변동 수요/발주 목표: 같은 기본품도 다음 회차에 다른 구매·진열 결정을 만든다. | 전역 순환 2가지 목표만 사용하고 보상/가격 배수는 생략한다. | 신규/기존 소유자가 다음 행동을 설명하는지, 공유재고 품절로 목표가 막히는지, 두 회차에서 실제 발주 선택이 바뀌는지 관찰한다. |
| 짧은 서버 영업대회: 판매 금액 밖의 실적을 드러내 신규 운영자도 비교에 참여한다. | 부문별 결과판과 개인 목표만 표시하고 종합 우승/경제 보상은 생략한다. | 초기 재산·부자손님·업그레이드 차이를 바꿔도 인정 거래가 같으면 점수가 같은지, 단순 운반 왕복 점수 농사가 없는지 검사한다. |
| 전문화·단골 관계: 자기 매장에 선택의 흔적을 남긴다. | 저장 없는 간판 테마 미리보기·선호 문구만 후속 후보로 둔다. | 첫 두 기능 이해도·저장 안정성 검증 뒤만 착수한다. 지금은 기한 내 필수가 아니다. |

NightShift-DesignReview는 게임 설명에서 관찰한 사실과 위 추론을 분리해 검토하고, 수요 접근성·대회 점수 농사·도난 영구자산 보호·구현 일정의 대안을 평가한다. 이 PM 문서는 자기 독립 검토를 대신하지 않는다. 채택 결정·사유·실제 테스트 연결은 [PM 계획](pm-release-plan.md)에 기록하도록 인계한다.
