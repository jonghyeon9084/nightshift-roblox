## SP1. 공간·팀·최종 목표
- 연결된 야간 동네 한 맵에 중앙 광장 Hub, 네 점포 Store01~Store04, 이를 잇는 거리와 짧은 골목을 둔다.
- 서버 온라인 인원 목표는 16명이다. Hub 대기자도 이 수에 포함하며 점포별 최대 좌석은 4개다.
- 팀은 별도 경쟁 진영이 아니라 해당 점포 근무 명단이다. 점포 간 점수 경쟁·방해·공유 불안도는 없다.
- 4점포는 같은 루프를 재사용하되 번호·텍스트 점포명·도형 간판·작은 입면 차이로 구별한다. 색만으로 나누지 않는다.
- 각 점포의 상품·표시판·차단기는 점포 안에서 접근한다. 주문 때문에 Hub나 다른 점포로 왕복할 필요는 없다.
- 확장용 맵 가설: 광장 폭 약 64 studs, 점포 중심을 광장에서 약 120~180 studs 거리에 배치, 연결 거리 폭 18 studs 이상.
- 크기는 탐색 가능한 거리/시야를 위한 출발값이다. 필수 이동 시간을 늘리는 빈 도로·차량 AI·새 추격 시스템을 추가하지 않는다.
- Hub에서 점포 선택 후 무료 이동 버튼으로 해당 Entry 근처로 이동할 수 있다. 걷기는 선택 사항이며 이동 대기 유료화는 없다.
- 점포 내부는 4명이 진열·계산·표시판에 서도 서로 막지 않는 넓이로 검증한다. 장식으로 마커/출입구를 가리지 않는다.

## SP2. 2·3·4인 주문 기여와 과제 축소
- 근무의 성공 단계는 항상 5건이며 활성 주문 묶음은 점포별 최대 1건이다. 3종 상품·한 사람 한 개 운반 원칙을 유지한다.
- 현재 협동 활성 인원 N에 대해 묶음 품목 수 Q=max(1,N-1)로 정한다. 2인/혼자는 1개, 3인은 2개, 4인은 3개다.
- 각 품목은 LineId·상품명·도형·상태(미수집/운반/계산대 대기/접수 완료, 축소 제외 시 취소 종결)를 가진다. 근무/주문/품목 ID를 함께 사용한다.
- 2인: 한 명이 상품을 찾고 Counter에 놓고, 다른 사람이 Counter의 ‘접수’ 버튼으로 품목을 확인한다.
- 3인: 두 명이 서로 다른 품목을 병렬 운반하고 한 명이 계산 접수한다. 다음 주문에서 계산/운반을 바꿀 수 있다.
- 4인: 세 명이 세 품목을 나눠 찾고 한 명이 도착 순서대로 접수한다. 계산 UI에 대기 품목과 남은 품목을 함께 표시한다.
- 역할은 추천이며 직업 잠금은 없다. 누구나 운반/접수 가능하고 운반자가 자신의 품목도 접수할 수 있다. 역할 독점은 관찰한다.
- Counter 기준의 세 가상 트레이 위치를 직접 만든 UI/Part로 표시한다. 새 인벤토리·컨베이어·제작 시스템은 필요하지 않다.
- 놓기는 해당 LineId의 첫 유효 요청만 허용한다. 접수는 Counter 범위의 활성 참가자만 하며 같은 품목은 한 번만 접수한다.
- 모든 필수 품목이 접수됐을 때만 주문 성공 수를 정확히 1 올린다. 3개 접수를 주문 3건으로 세지 않는다.
- 제한 45초 만료 시 미완료 묶음 전체에 +15를 한 번 부과한다. 부분 접수로 성공 단계를 올리지 않으며 새 OrderId로 같은 단계 재요청한다.
- 만료·성공·취소 때 그 주문의 잔여 상품/트레이를 회수한다. 이전 주문 상품을 다음 주문에 제출할 수 없다.
- A/B의 단계 3~5, C의 단계 2~4에는 각각 다른 기본 상품을 첫 품목으로 배정한다. 추가 품목은 다른 상품으로 채운다.
- 시작 인원이 유지되면 변경 뒤 세 종류를 찾는다. 감소 조정으로 일부 품목이 취소되어도 최소 3개 후속 성공 단계의 새 수집은 유지한다.
- 4→3→2명은 점포를 멈추지 않고 즉시 Q를 낮춘다. 이미 접수한 품목은 취소/차감하지 않는다.
- 현재 목표 수는 max(이미 접수한 수, 새 Q)다. 접수 품목 모두와 필요한 수만큼의 미접수 품목만 유지한다.
- 유지할 미접수 품목은 SP2.2의 회수/미수집 복원을 먼저 마친 뒤 계산대 대기→유효 운반 중→미수집 순, 같은 상태는 LineId 순으로 선택한다. 나머지는 취소·무료 회수한다.
- 축소만으로 현재 목표를 이미 충족하면 주문을 한 번 완료하고 정상 사건 경계를 진행한다. 완료했던 주문은 다시 축소 처리하지 않는다.
- 감소 시 주문 ID·잔여 시간·불안도·성공 수를 보존하며 추가 이탈 벌점은 없다. 향후 주문은 감소된 Q로 생성한다. 1명 복구 대기 중에는 감소 직전 과제 구성을 잠시 보존하고, 2명 이상 재개 또는 혼자 확정 시 그 확정 인원에 맞춰 한 번 축소한다.
- 인원 증가로 진행 중 과제를 늘리지 않는다. 도중 신규 합류자는 다음 근무 대기이므로 현재 N과 Q에 포함되지 않는다(SP5).
- 사례: 4인에서 두 품목 접수 후 한 명 이탈하면 Q=2로 조정되어 그 묶음은 완료된다. 남은 세 명은 다음 묶음 2개를 운반/접수한다.
- 4인 중 둘이 계속 구경하는지를 품목별 운반·접수/정전 구간 공유 기록으로 확인한다. 수량 증가만으로 재미를 달성했다고 보지 않는다.

### SP2.1. 품목 상태 전환과 소유권 — S1

- LineId마다 LineRevision을 두며 성공한 상태 변경마다 증가시킨다. 집기는 서버가 발급한 CarryToken과 운반자 ID를 함께 지정한다.
- 집기 요청은 현재 LineRevision을, 놓기/반납은 현재 LineRevision·CarryToken을 요구한다. StoreId/활성 권한/주문 유효성·거리·한 사람 한 개 제한도 검사한다.
- 상태 검사와 운반자/트레이 기록 변경, 개인 운반 슬롯 갱신, 시각 상품 생성/제거는 같은 직렬 처리 단위다. 한 LineId에는 유효 운반자 최대 1명 또는 트레이 최대 1개만 존재한다.

| 이전 상태 | 유효 행동/조건 | 다음 상태와 서버 기록 |
| --- | --- | --- |
| 미수집 | 활성 참가자의 해당 진열대 집기, 손이 비어 있고 현재 Revision 일치 | 운반: 운반자 1명·새 CarryToken 지정, Revision 증가. 같은 상태를 본 두 번째 집기는 거부 |
| 운반 | 현재 운반자/Token/Revision이 일치하는 Counter 놓기 | 계산대 대기: 운반자/Token·개인 운반 슬롯 제거, 해당 LineId의 트레이 1개 지정, Revision 증가 |
| 운반 | 현재 운반자/Token/Revision이 일치하는 무료 반납 | 미수집: 운반자/Token·개인 운반 슬롯·시각 상품 제거, 트레이 없음, Revision 증가. 같은 LineId 재수집 가능 |
| 운반 | 운반자 이탈·대기자 전환·캐릭터 제거로 권한 소멸 | 미수집: 반납과 같은 소유권/상품 회수 및 Revision 증가. 그 후에만 SP2.2 축소 선정 |
| 계산대 대기 | 활성 참가자의 현재 Revision 확인 후 Counter 접수 | 접수 완료: 트레이 제거, 운반자 없음, 접수 이력 저장, Revision 증가. 품목 접수는 한 번 |
| 계산대 대기 | 이전 운반자의 이탈/대기자 전환 | 그대로 유지: 소유자는 개인이 아닌 점포 트레이. 이전 운반자 때문에 미수집으로 되돌리지 않음 |
| 접수 완료 | 이전 운반자/접수자의 이탈·대기자 전환·일반 반납 요청 | 접수 유지: 운반자/트레이 없음. 반납은 거부, 접수 수를 차감하지 않음 |
| 미접수 모든 상태 | SP2.2 축소에서 취소 대상으로 결정 | 취소: 운반자/Token·개인 슬롯·트레이·시각 상품 해제, Revision 증가, 그 주문에서 재수집 불가 |
| 모든 상태 | 주문 만료/완료·근무 종료 | 해당 주문 소유권/트레이 폐기, 과거 ID 요청 거부. 접수 이력은 결과/중복 판정용으로만 보존 |

- 일반 반납은 현재 손에 든 품목만 대상으로 한다. 계산대 대기 품목은 접수 또는 시스템 축소/주문 종료로만 처리하며, 이전 운반자가 원격 반납으로 지울 수 없다.
- 놓기/반납/회수/취소 뒤 이전 CarryToken은 폐기한다. 같은 사람이 같은 LineId를 재수집해도 새 Token을 사용하므로 이전 놓기·반납 요청은 거부한다.
- 같은 요청 ID 재전송은 기존 처리 결과만 돌려주고 상태를 다시 바꾸지 않는다. 서로 다른 놓기/반납 요청이 같은 시각이면 SP6 접수 순번의 첫 유효 요청만 성공한다.

### SP2.2. 회수·복원·과제 축소 순서 — S1

1. 감소/전환 대상의 활성 권한을 제거한다. 해당 대상이 운반 중인 각 LineId의 운반자·Token·개인 슬롯·시각 상품을 해제하고 미수집으로 복원하며 Revision을 증가시킨다.
2. 그 사람이 과거 운반했던 계산대 대기는 트레이로 유지하고 접수 완료는 접수 이력으로 유지한다. 유효한 잔여 참가자의 운반 상품은 보존한다.
3. SP6에 따라 이미 도달한 기한을 처리한다. 주문/근무가 종료됐다면 종료 정리로 끝내며 같은 주문을 축소/재완료하지 않는다.
4. 진행할 확정 인원에 맞춰 Q와 현재 목표 수를 계산한다. 접수 완료를 모두 보존하고, 복원 후 상태를 기준으로 필요한 미접수 품목을 선정한 뒤 나머지를 취소한다.
5. 유지된 미접수 품목마다 ‘미수집이며 재수집 가능 / 활성 운반자와 현재 Token 존재 / 점포 트레이 존재’ 중 정확히 하나가 성립하는지 검사한다. 고아 운반·복수 운반·중복 트레이는 허용하지 않는다.

- 이탈·강등 대상의 운반품은 축소 전에 강제로 미수집 복원한다. 이 복원은 해당 대상에게만 적용하며, 남은 활성 참가자의 일반 반납 요청을 앞당겨 실행하는 규칙이 아니다.
- 남은 활성 참가자의 일반 반납은 참가자 권한과 Q를 유지하며, 같은 서버 수신 시각의 이탈·기한·축소 처리가 끝난 뒤 일반 입력 순서로 처리한다. 축소 선정에는 그 반납이 아직 실행되지 않은 유효 운반 상태를 사용한다.
- 유지 선정만으로 남은 운반품의 LineRevision·CarryToken이나 운반자의 좌석 세대를 바꾸지 않는다. 축소 후에도 유지됐고 요청이 유효하면 반납하여 미수집으로 복원한다. 이미 취소됐으면 이전 Token 요청을 거부한다.
- 일반 반납이 더 이른 서버 수신 시각에 이미 확정됐다면 그 미수집 상태를 뒤 시각 이탈/축소의 선정 기준으로 사용한다. 같은 시각 일반 반납은 접수 순번이 작아도 이탈/축소를 앞서지 않는다(SP6).
- 1명 복구 대기 중에도 대상 품목 회수/미수집 복원은 즉시 수행한다. 과제 축소만 확정 인원으로 재개/혼자 확정할 때까지 미룬다.
- 온라인 혼자 전환으로 대기자가 된 사람의 운반품에도 같은 순서를 적용한다. 남은 진행자의 유효 운반품은 보존하고 트레이/접수 상태는 위 표를 따른다.

## SP3. 다인 정전·정보 소유권
- 사건 순서 A/B/C, 진열 변경 1회, 정전 1회, 순서 원·삼각·사각, 45초 자동 복구는 v0.2 P3~P5를 유지한다.
- 공동 정전에는 활성 N명 중 차단기 조작자 1명과 표시판 정보 담당 N-1명의 서로 다른 소유자가 필요하다.

| 활성 N | 표시판 구간 | 차단기 | 플레이 사례 |
| --- | --- | --- | --- |
| 2 | 1명이 도형 1~3 전체 확인/공유 | 다른 1명이 세 도형 입력 | A가 전체 순서를 공유, B가 입력 |
| 3 | A가 도형 1~2, B가 도형 3 확인/공유 | C가 전체 순서 입력 | 앞 구간과 마지막 구간을 합쳐 해결 |
| 4 | A/B/C가 도형 1/2/3 각각 확인/공유 | D가 전체 순서 입력 | 세 운반자가 표시판 앞 세 자리로 모여 정보를 나눔 |
| 1 확정 | 순서 전체 직접 제공 | 유일 진행자가 입력 | 단독 해결로 구분, 공동 해결 아님 |

- SignalPanel 한 개의 좌우 가상 자리/구간 버튼을 재사용한다. 별도 방 세 개나 새 퍼즐 종류를 만들지 않는다.
- 읽기 역할은 빈 구간을 서버에서 원자적으로 선점한다. 한 사람은 한 구간 또는 Breaker만 소유할 수 있다.
- 각 담당은 현장에서 연결하고 직접 구간 공유를 누른다. 전체 공유가 완료되기 전 차단기는 ‘아직 공유 안 된 구간’을 표시한다.
- 차단기는 모든 구간의 현재 유효 소유자가 연결되어 있고 조작자가 그들과 다를 때만 입력을 허용한다.
- 공유 정보는 정전 종료까지 지속하며 위치 신호만 5초다. 구간/입력 진도/연결 중지 이유를 무음 UI로 보여준다.
- 같은 N에서 소유자의 이동·취소·역할 교환·일시적 클라이언트 미로드는 소유권을 해제하고 입력을 중지하되 공유/진도를 유지한다.
- 빈 구간/차단기는 같은 점포의 다른 활성 참가자가 다시 선점할 수 있다. 과거 소유자의 늦은 입력은 소유권 세대 번호로 거부한다.
- 정전 중 4→3→2명으로 확정 감소하면 N을 즉시 낮추고 구간을 표에 맞춰 재분할한다. 모든 정전 소유권·구간 공유·입력 진도를 초기화한다.
- 이때 정전 ID·정답 세 도형·유효 경과 시간·이미 부과한 벌점은 유지한다. 무료 재공유 안내를 띄우며 추가 벌점은 없다.
- 재분할로 공동 해결이 어려워진 사례는 기록한다. 시간을 초기화해 반복 이탈로 45초를 무한 연장하지 않는다.
- 복구 대기 중에는 소유권 모두 해제, 공유와 진도 보존. 같은 명단으로 복구되면 다시 선점 후 이어간다.
- 복귀 후 명단 수가 달라졌다면 위 재분할을 적용한다. 혼자 확정은 전체 직접 공개·진도 0·표시판 요구 해제다.
- 오입력은 진도만 0, 공유와 소유권 유지다. 정전 종료/근무 종료/전원 이탈은 소유권·공유·진도를 폐기한다.
- 정전 전 혼자 확정/혼자 연습도 사건을 생략하지 않는다. 발생 때부터 단독 입력 규칙을 적용한다.
- 정전 후 인원 감소도 결과 이력에 남긴다. 한 번 지원 복구가 나왔거나 혼자 모드가 확정되면 정상 공동 결과로 되돌리지 않는다.

### SP3.1. 첫 밤 메모·도움말·HUD 대체 — S2

- 확장판은 v0.2 P8의 “매장 한 명, 차단기 한 명” 메모와 같은 의미의 고정 2인 도움말을 사용하지 않는다. 2인 회귀판 원문은 그대로 보존한다.
- 확장 첫 밤 메모: “주문 5건. 불이 꺼지면 표시판 담당들이 구간을 공유하고, 차단기 담당이 순서를 입력하세요. 필요한 인원은 화면에서 확인해요.”
- 정전 도움말: “각자 빈 역할을 맡으세요. 표시판 담당 전원이 연결해 구간을 공유하면 차단기에서 순서를 입력할 수 있어요.”
- HUD는 SP3의 같은 구간 분할 상태에서 ‘표시판 필요 N-1명 / 연결 x명 · 차단기 필요 1명 / 연결 여부’, 각 구간 담당자·연결/공유 여부·누락 구간 번호를 표시한다.
- 2인은 표시판 1명(1~3번), 3인은 2명(1~2번/3번), 4인은 3명(각 1개)으로 표시한다. 차단기 담당은 항상 별도 1명이다.
- N 변경 재분할은 역할 요구 수·구간 번호·도움말·공유/진도 초기화 UI를 같은 상태 Revision으로 갱신한다. 예: “인원 조정: 표시판 2명, 차단기 1명. 구간을 다시 공유해 주세요.”
- 복구 대기 중에는 ‘복귀 대기 · 입력 중지’와 보존 중인 구간을 표시하고, 이를 현재 입력 가능으로 표현하지 않는다. 재개/혼자 확정 후 확정 상태로 갱신한다.
- 혼자 확정/혼자 연습의 도움말은 “혼자 마무리: 표시판 연결 없이 화면 순서를 차단기에 입력하세요.”로 대체한다. HUD는 ‘표시판 필요 0명 · 차단기 1명’과 전체 순서를 표시한다.
- 역할 수·공유·연결의 실제 입력 조건과 UI 표시를 각각 따로 계산하지 않는다. 같은 서버 상태를 사용하며 누락 구간을 소리/색만으로 안내하지 않는다.

## SP4. StoreId별 상태·권한·통신
- 식별자 집합은 Store01~Store04로 고정한다. 서버 내부 점포 상태가 권위이며 맵 인스턴스 존재/클라이언트 UI가 근무 상태를 소유하지 않는다.

| 범위 | 보관할 상태/규칙 |
| --- | --- |
| 서버 전체 | 온라인 최대 인원, Player→점포 좌석 매핑, 접수 순번, 서버 시계. 점포 간 공유 주문/불안도는 없음 |
| 점포 | 좌석 4개, 로비 명단 버전, 준비, 현재 RoundId, 근무 상태, 대기자/복귀 예약, 직전 일정/배치 |
| 근무 | 시작/현재 활성 명단, N·Q, 성공 단계, 불안도, 300초 유효 경과, 사건 큐, 복구 누적 20초, 인원 감소/혼자/지원 이력, 결과 |
| 주문 | OrderId, 단계, LineId별 상품/상태/LineRevision·운반자/CarryToken·트레이, 만료 잔여, 한 번만 완료/만료되는 확정 상태 |
| 정전 | OutageId, 정답, 구간 분할, 공유, 소유자/세대, 입력 진도, 경과, 벌점 부과 이력, 처리 방식 |
| 참가자 | 활성/대기/복귀 준비/Hub, 좌석 세대, 운반 상품, 맡은 정전 역할. 타 점포 권한 없음 |

- 요청은 StoreId·RoundId·대상 OrderId/LineId 또는 OutageId·행동·요청 ID·명단/소유권 세대를 필요한 범위에 포함한다. 품목 요청은 SP2.1의 LineRevision과 필요한 CarryToken을 추가 검사한다.
- 서버는 사용자→점포 매핑, 활성 명단/대기 권한, ID 유효성, 상태, 위치/거리, 상품/역할 소유권을 다시 검사한다.
- 예: Store02 참가자가 Store01 주문/Breaker 요청을 보내면 상태를 바꾸지 않고 거부한다. StoreId 인자만 바꿔 팀을 바꿀 수 없다.
- 다른 점포에 걸어 들어가도 관람만 가능하다. 타 점포 상호작용은 비활성, 직접 원격 요청은 서버가 거부한다.
- 이전 근무/주문/품목·삭제된 소유권·이동 전 좌석 세대의 요청은 거부한다. 결과 확정 뒤 입력으로 재개하지 않는다.
- 같은 품목 집기/반납/놓기/접수·시스템 회수/복원/축소, 주문 완료, 사건 시작/종료, 결과 확정, 좌석 이동은 각각 직렬·원자 처리하고 재전송은 중복 처리하지 않는다. 이탈/대기자 전환과 품목 축소 사이에 일반 품목 요청을 끼워 넣지 않는다.
- 같은 시각 남은 참가자의 일반 반납도 이탈·기한·축소 후 검사한다. 생존자의 유지된 품목/좌석 세대는 보존하고, 로비 준비용 명단 버전 변경만으로 그 유효 반납을 거부하지 않는다. 더 이른 시각에 확정된 반납 상태는 이후 축소에 반영한다.
- 클라이언트에는 본인 점포의 필요 상태만 전송한다. 타 점포는 점포명·인원·로비/진행/결과·빈 좌석 요약만 보인다.
- 정답 구간은 읽기 담당에게 보내고 직접 공유 후 팀 UI로 공개한다. 신규 소유자는 자기 구간만 읽으며 이전 공유 내용은 유지한다.
- 상태 메시지는 StoreId/RoundId/Revision을 포함한다. 늦은 Revision은 폐기하고 누락 시 제한된 스냅샷 재요청으로 복구한다.
- 타 점포의 이탈/재시작은 해당 점포 타이머·명단·소유권만 바꾼다. 서버 전체 근무를 멈추지 않는다.

## SP5. 좌석·합류·준비·감소·재결성
- 좌석 수에는 온라인 활성/대기자와 복구 대기 중 오프라인 예약을 합산한다. 한 사용자는 한 점포 좌석만 차지한다.
- Hub는 팀 미선택 상태다. 명시적 점포 선택 요청을 서버가 확인한 뒤 빈 좌석 하나를 배정하고 준비=false로 둔다.
- 5번째 요청은 ‘정원 4명’을 반환하며 Hub에 남긴다. 마지막 좌석 동시 요청은 서버 접수 순번이 빠른 한 명만 성공한다.
- 자동 이동/자동 합류 대기열은 만들지 않는다. 사용자가 빈 점포를 다시 선택할 수 있다. 정원/이동은 무료다.
- 로비 준비 요청은 현재 명단 버전에만 유효하다. 합류/퇴장/팀 이동 시 버전을 올리고 남은 전원 준비를 취소한다.
- 2~4명 전원 준비하면 3초 시작 확인 상태로 간다. 그동안 준비 취소/명단 변경 시 시작을 취소한다.
- 시작 확인 3초 만료와 같은 시각 취소는 늦다. 먼저 근무 명단을 고정하며 이후 퇴장 요청은 진행 중 이탈로 처리한다.
- 근무 도중 빈 좌석 합류는 ‘다음 근무 대기’다. 현재 주문/정전/목표량을 바꾸거나 진행 입력을 보낼 수 없다.
- 진행 중 자기 팀 변경은 먼저 현재 점포 퇴장 요청으로 처리한다. 다른 점포 좌석 획득은 퇴장 완료 후 별도 요청이며 확보를 보장하지 않는다.
- 로비/결과에서 팀 이동은 목표 정원 확인과 원팀 좌석 해제/새팀 배정을 한 번에 처리한다. 실패하면 원좌석을 유지한다.
- 활성 참가자 자발 퇴장/접속 끊김/캐릭터 재생성은 같은 명단 감소로 처리한다. SP2.1~SP2.2에 따라 운반품을 회수·미수집 복원한 뒤 축소하고 정전 역할을 해제한다. 계산대 대기/접수 완료를 개인 상품으로 회수하지 않는다.
- 활성 4→3 또는 3→2는 즉시 계속 진행하고 SP2/SP3를 조정한다. 해당 이탈자는 좌석을 즉시 잃으며 돌아와도 신규 대기자다.
- 활성 인원이 1이 되면 남은 사람을 기준으로 복구 대기한다. 상품/역할 입력과 근무·주문·정전·경계 타이머를 모두 정지한다.
- 복구 예산은 점포 근무당 누적 최대 20초다. 반복 이탈/복귀/씬 미로드로 새 예산을 만들지 않는다.
- 이 복구를 유발한 감소 직전 활성 명단의 접속 끊김/캐릭터 제거 대상만 남은 예산 동안 복귀 예약을 갖는다. 이전 4→3→2 단계 이탈자와 명시적 점포 퇴장자는 대상이 아니다. 예약 후보가 없거나 예산이 0이면 즉시 혼자 확정한다.
- 복귀 예약은 원좌석을 점유한다. 예약 참가자만 ‘복귀 준비’로 들어오며, 대기자는 빈자리가 있어도 현재 근무로 승격되지 않는다.
- 예약 참가자가 복귀 대신 Hub/다른 팀을 명시적으로 선택하면 원점포 예약을 먼저 해제한다. 예약과 새 좌석을 동시에 보유하지 않으며 마지막 예약이 없어지면 남은 사람을 즉시 혼자 확정한다.
- 남은 사람과 복귀 준비자 중 연결된 대상 모두 준비하고 총 2명 이상이면 기한 전 재개한다. 아직 안 돌아온 예약은 해제하며 그 사람은 추후 대기 합류만 가능하다.
- 재개 활성 명단이 감소 전과 같으면 정전 공유/진도 유지, 다르면 SP3 재분할을 적용한다. 재개 전부터 지난 기한은 소급 취소하지 않는다.
- 남은 사람은 즉시 혼자 마무리 또는 퇴장을 선택할 수 있다. 예산 만료 시 그 사람이 연결되어 있으면 자동으로 유일 진행자로 확정한다.
- 남은 사람도 떠나 활성/복귀 준비자가 0명이 되면 즉시 근무를 폐기한다. 오프라인 예약만으로 빈 근무를 유지하지 않는다.
- 남은 사람이 떠날 때 복귀 준비자가 연결되어 있으면 그중 기존 좌석 번호가 가장 작은 한 명을 새 남은 사람으로 삼고 같은 예산/기한을 이어간다.
- 혼자 확정 시 예약은 해제하고 접속 복귀자는 다음 근무 대기다. 다른 온라인 대기자와 현재 진행자 권한을 혼동하지 않는다.
- 혼자 모드는 해당 근무 동안 되돌리지 않는다. 유일 진행자 이탈 시 근무를 종료하고 대기자에게 진행권을 넘기지 않는다.
- 활성 2명일 때만 v0.2의 온라인 무응답 혼자 전환 요청을 허용한다: 근무당 1회·10초 취소 기회·먼저 접수한 요청 하나·정각은 전환 우선.
- 활성 3~4명에게 동료 여러 명을 대기자로 강등하는 요청은 없다. 응답하지 않는 동료 때문에도 45초 지원 복구/300초 종료로 끝날 수 있고 본인 퇴장은 가능하다.
- 온라인 요청 중 명단 감소/결과 확정이면 요청 취소 후 해당 감소/종료 규칙을 따른다. 성공 시 요청자만 활성, 상대는 대기자로 전환하고 SP2.2의 회수·복원→기한 판정→축소 순서를 적용한다.
- 로비에서 한 명은 혼자 연습을 명시적으로 선택할 수 있다. 다른 대기자가 있거나 2명 이상이면 정상 전원 준비 또는 퇴장 선택을 사용한다.
- 혼자 연습은 N=1/Q=1, 정전 전부터 단독 규칙, 결과는 인원 조정이다. 연습 도중 합류자는 다음 근무 대기다.
- 결과 뒤 현재 온라인 좌석자는 모두 로비/준비=false가 된다. 대기자도 다음 명단에 포함하며 2~4명 전원 준비로 재결성한다.
- 전원 이탈/근무 폐기 시 예약·상품·소유권·타이머를 해제한다. 온라인 대기자가 있으면 좌석을 유지한 로비로, 없으면 빈 점포가 된다.
- 새 근무는 새 RoundId와 빈 주문/정전/결과 상태로 시작한다. 슬롯 재사용으로 이전 사용자의 권한을 복원하지 않는다.

## SP6. 경계 시각·결과 우선순위
- 서버 수신 시각과 단조 접수 순번을 사용한다. 동일 시각은 연결/자발 퇴장/캐릭터 제거 → 300초 기한 → 준비 시작/복구/온라인 전환 기한 → 정전/주문 기한 → 일반 입력 순이다.
- 같은 시각의 좌석 합류/이동/준비 등 일반 요청은 전역 접수 순번대로 처리한다. 좌석 변경과 연동 준비 무효화는 한 처리 단위다.
- 퇴장이 타이머를 정지시켜도 그 시각까지 이미 경과한 기한은 처리한다. 기한 정각 요청을 기한 이전으로 소급하지 않는다.
- 이탈은 먼저 권한/명단에서 제거하고 SP2.2의 운반품 회수·미수집 복원을 마친 뒤, 이미 도달한 기한을 처리하고 SP2/SP3 과제를 축소한다. 기한 전 감소라면 축소 완료 판정을 즉시 적용한다. 주문/정전/결과는 각각 한 번만 확정한다.
- 위 강제 복원 대상은 이탈·강등된 운반자뿐이다. 남은 참가자의 같은 시각 일반 반납은 이탈·기한·축소 완료 후 일반 입력 단계에서 검증/처리한다. 접수 순번은 같은 우선순위 안에서만 비교하며 더 이른 수신 시각에 확정된 반납은 소급하지 않는다.
- 같은 시각 여러 이탈은 모두 제거한 뒤 잔여 수로 한 번 조정한다. 잠깐 1명인 중간 상태로 혼자 모드를 잘못 확정하지 않는다.
- 300초 상한, 불안도 최대 실패, 45초 자동 복구, 유효 입력은 v0.2처럼 기한 우선이다. 정확히 45초 해결은 지원 복구다.
- 2~4명 유지+공동 해결+목표 완료는 협동 성공, 지원 복구면 지원 마감이다. 4→3→2 이력은 ‘인원 감소’ 부기로 구별한다.
- 혼자 확정/혼자 연습 이력이 한 번이라도 있으면 목표 완료는 인원 조정·마감이다. 미완료는 원인과 인원 이력을 함께 표시한다.
- 모든 결과의 무료 재도전/일정 접근은 같다. 결과·불안도·성공 수를 다른 점포와 합치지 않는다.

## SP7. 맵 마커·스트리밍·유한 복구
- 기본 경로: Workspace.NightShiftWorld 아래 Hub와 Stores, Stores 아래 Store01·Store02·Store03·Store04를 둔다.
- 각 점포 모델의 StoreId 속성은 모델명과 같아야 한다. 점포 마커 Counter·Shelf1·Shelf2·Shelf3·SignalPanel·Breaker·Entry·Spawn은 각 점포 내부에 각각 하나다.
- Hub의 Spawn/점포 선택 지점 세부 형식, 마커 타입/로컬 오프셋은 구현 메인이 계약으로 고정한다. 본안의 마커 이름과 StoreId는 임의 변경하지 않는다.
- Counter는 SP2의 트레이 3개 기준점, SignalPanel은 SP3의 구간 자리 3개 기준점이다. 별도 필수 마커를 늘리지 않는다.
- 서버 시작 검사는 네 StoreId 유일성/필수 마커 중복·누락/안전 Spawn을 확인한다. 오류 점포는 선택 불가로 표시하며 다른 점포는 유지한다.
- 클라이언트는 경로 문자열/StoreId로 다시 바인딩한다. 사라질 수 있는 Instance 참조를 영구 캐시하거나 이를 주문/정답 상태 원본으로 쓰지 않는다.
- HUD·점포 요약·팀 상태는 Workspace 로드 여부와 독립인 상태 메시지로 유지한다. 맵 미로드를 팀 이탈/신규 근무로 오인하지 않는다.
- 처음 선택/이동 시 필수 마커 탐색은 최대 5초, 실패하면 입력을 끄고 ‘점포 준비 중’·재시도·Hub 복귀를 제공한다. 무기한 WaitForChild는 쓰지 않는다.
- 자동 재시도는 2초 뒤 한 번만, 재탐색도 최대 5초다. 총 자동 시도 2회 뒤에는 명시적 재시도 버튼 또는 Hub 복귀만 제공한다.
- 이 로딩 상태에서는 로비 준비를 켤 수 없다. 시작 확인 중 필수 마커가 해제되면 로드 상태 해제/준비 취소를 요청한다. 접수 전에 근무가 시작됐다면 아래 진행 중 복구 규칙을 적용한다.
- 진행 중 필수 마커/상호작용 대상 해제 시 관련 프롬프트를 즉시 해제하고 들고 있던 로컬 시각 효과만 숨긴다. 서버 상품 ID는 유지한다.
- 해당 정전 소유자는 클라이언트 해제 알림 또는 서버 거리/생존 검사 실패 시 소유권을 해제한다. 알림은 자기 소유권만 반납할 수 있고 타인의 역할을 해제하지 못한다.
- 서버 역할 연결은 2초 주기 갱신, 마지막 갱신 후 5초 만료 가설로 유한 해제한다. 갱신도 실제 거리·활성·같은 점포를 검사한다.
- 로컬 미로드만으로 점포 타이머를 멈추거나 과제를 줄이지 않는다. 허위 로드 실패로 팀 시간을 무한 정지시킬 수 없다.
- 마커 재등장 때 프롬프트를 한 번만 재연결하고 점포 스냅샷을 다시 받는다. RoundId/Revision을 확인해 오래된 운반·입력 UI를 복원하지 않는다.
- 재로딩에도 같은 5초+재시도 1회 한도를 쓴다. 실패 UI에서 무료 ‘내 점포 Spawn으로 재배치’ 또는 ‘점포 퇴장 후 Hub’ 요청을 제공한다.
- 재배치는 같은 점포/안전 서버 Spawn만 허용하고 10초당 한 번, 역할을 해제한다. 팀 상태·불안도·시간은 초기화하지 않는다.
- Hub도 미로드면 오버레이와 재시도/상태 표시를 유지한다. 안전 위치 확인 실패 시 서버가 임의 좌표에 떨어뜨리지 않고 이동 실패를 반환한다.
- 스트리밍 활성화/범위/모델 모드는 메인이 실제 측정으로 정한다. 전 도시를 영구 상주시켜 문제를 덮는 것을 기본안으로 삼지 않는다.
- 공식 근거 확인일 2026-10-31: [Instance streaming](https://create.roblox.com/docs/workspace/streaming). Workspace 콘텐츠는 로드/해제될 수 있으므로 위 재바인딩 설계를 적용한다. 특정 설정이 성능을 보장한다는 뜻은 아니다.

- 예산을 맞추기 위해 주문 단서·정전 도형·필수 마커·무료 기능을 삭제하지 않는다. 필요하면 장면 밀도를 먼저 줄인다.
- 5Hz 델타 제한 중 결과/권한 변경은 다음 200ms 이내에 전송한다. 여러 변경을 한 델타로 합치고 UI는 Revision으로 순서를 확인한다.
- 역할 연결 갱신은 상태 변경 입력과 구분하되 위 전체 요청 계측에 포함한다. 악의적 스냅샷 재요청/거부 입력도 점포 간 지연을 만들지 않게 제한한다.
- 바이트 예산은 게임 메시지 추정치다. 엔진 전체 네트워크 사용량/지연도 별도로 기록하고 숫자 단위와 측정 도구를 남긴다.
- 공식 근거 확인일 2026-10-31: [Improve performance](https://create.roblox.com/docs/performance-optimization/improve). 매 프레임 고비용 처리·남은 연결·불필요한 물리를 줄이는 방향을 참고했다. 위 숫자는 자체 가설이다.

## SP10. 인계와 미검증 경계
- 메인은 SP4의 서버 상태/원격 필드, SP7의 마커 형식/스트리밍 설정, SP8의 계측 방법을 구현 전에 공유 규약으로 확정한다.
